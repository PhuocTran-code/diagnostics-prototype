Master patient index on a medallion architecture

Business problem: patient identity is fragmented across two laboratory systems (lis_a, lis_b) and one radiology system (ris), each with its own patient identifier. The solution resolves every source record to a single mpi_id in the silver layer, and every analytic fact in gold joins on that one identifier. Companion files: diagnostics_source_schemas.sql (sources) and silver_master_patient_index.sql (tested matching logic).

1. Conceptual model

One PATIENT is the person. Each system holds its own SOURCE_PATIENT_RECORD for that person under a different identifier. Diagnostic activity attaches to the person, not to any one system's record.

  • A patient must have at least one source record and may have one per system. Three records for one person is the normal case for a patient who has used pathology at both labs and had imaging.
  • The match rule is part of the model, not an implementation detail. Being able to say "these two records were linked on Medicare number and date of birth" is what makes the index auditable.
  • Requests hang off the person. Reporting a patient journey across pathology and imaging is a single join once the index exists.

2. Logical model

Two parts: the MPI tables in silver where matching happens, and the gold star schema that consumes the resulting identifier.

2b. Gold: star schema keyed on the MPI

3. Solution architecture

Standard medallion flow with the MPI as the defining step in silver. Facts cannot be loaded to gold until their patient has an mpi_id.

  • Bronze proves the fragmentation: three patient tables, three id formats, three date formats, side by side.
  • Silver step 2 is the only place identity is decided. Clinical entities in step 3 look up mpi_id through the crosswalk and never carry a source patient id forward on its own.
  • Gold has exactly one patient dimension row per person. A pathology result from lis_a, a result from lis_b and a CT from ris for the same person all join to the same patient_key.
  • Audit adds MPI specific measures to the workshop pattern: records matched per tier, records left unmatched, and Medicare numbers found in more than one cluster (which should always be zero).
  • Known limits for the report: deterministic rules cannot recover from a mistyped Medicare number or date of birth, and mpi_id values are regenerated on each full rebuild. A production build adds probabilistic scoring, a steward review queue, and persistent identifiers.

4. Dashboard layer

Three pre-aggregated SQL views sit on top of the gold layer in a dashboard schema. A Metabase instance (http://localhost:3030) renders them as interactive bar charts. No BI-tool user ever touches a fact table directly.

Views in the dashboard schema (pipeline/08_dashboard_views.sql)

ViewSource tablesWhat it answers
v_turnaround fact_pathology_result, fact_imaging_study, dim_site, dim_date Average, median (p50) and 90th-percentile (p90) turnaround time in minutes, broken down by site, priority (ROUTINE / URGENT), request type (PATHOLOGY / IMAGING), year and month. Both request types are unified with a UNION ALL so one view covers the whole service. Imaging turnaround_hours is multiplied by 60 so both streams share the same minute scale.
v_abnormal_rate fact_pathology_result, fact_imaging_study, dim_site, dim_date, dim_test, dim_procedure Abnormal result percentage for pathology tests (is_abnormal) and critical finding rate for imaging studies (critical_finding), by site, test or procedure code, year and month. NULL fills keep both streams in one view schema — pathology rows carry NULL for critical_count and imaging rows carry NULL for abnormal_count.
v_mpi_impact silver.patient_source, gold.dim_patient, silver.patient_xref Headline MPI metrics in a single row: raw source identifiers, golden patients, duplicates collapsed, collapse rate %, and a count breakdown by match basis (Tier 1 medicare+dob, Tier 2 name+dob+sex, unmatched (single source)). This view crosses silver and gold — it is the only place in the dashboard schema that reads silver tables.

Metabase charts (http://localhost:3030)

Three charts are assembled into the MedScan Diagnostics Dashboard. Each chart is a native SQL question pointing at one view.

ChartViewChart typeKey finding on the synthetic dataset
Abnormal Rate by Test (Pathology) v_abnormal_rate Bar chart Average abnormal % per test name, pathology only, sorted descending. Shows which tests produce the most out-of-range results across all sites — Haemoglobin sits at the top of the synthetic data.
Turnaround Time by Site (Pathology) v_turnaround Grouped bar chart (ROUTINE vs URGENT) Average turnaround in minutes per site. ROUTINE bars are consistently higher than URGENT, confirming that priority triage is working as designed across all collection centres.
MPI Impact Summary v_mpi_impact Bar chart Raw identifiers (108) vs golden patients (63) vs duplicates collapsed (45). The 41.7 % collapse rate is the headline evidence that the MPI is working — without it, every cross-system query would double- or triple-count the same person.
  • All three views read only from gold (and silver for v_mpi_impact metadata). No PII reaches the BI layer because dim_patient carries no names, dates of birth, or Medicare numbers.
  • The views are idempotent: 08_dashboard_views.sql drops and recreates them on every pipeline run, so schema changes in gold flow through automatically on the next run.
  • Metabase connects to the medscan database as student / student on host postgres, port 5432. Charts are saved as native SQL questions and persist across restarts via the ./data/metabase Docker volume.
  • The Metabase service is defined in docker-compose.yml (port 3030 on the host, 3000 inside the container) and depends on the postgres service so it starts only after the database is ready.
Synthetic data and identifiers throughout. Matching rules are illustrative and would be validated against real data quality before use.
